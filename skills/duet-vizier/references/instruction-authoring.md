# Writing agent instructions

Read this before you create or revise any text that agents work from: a skill (its `SKILL.md`, references, scripts and tests), a system prompt, an agent definition, a command, or similar text written for agents to follow. All of these are instructions, and the rules below apply to each of them. The file is written for whoever does the writing: usually an agent assigned to the task, sometimes the agent coordinating the work.

Before you start, you must load the skill-creation skill that your client's vendor ships and follow it: Anthropic's `skill-creator` in Claude clients, OpenAI's `skill-creator` in Codex. Each vendor's guide describes how its own models read instructions, so use the one that matches the agent doing the work, and load it through the client's skill mechanism. For a skill, follow it in full except its advice on triggering, which the next section replaces; for other instructions, apply its guidance on writing instructions wherever it fits. This file adds the rules that `skill-creator` does not cover.

## The model never chooses a skill

Every skill you write or revise under these rules is loaded in one of two ways, or in both. Either only the user invokes it, and it is marked with `disable-model-invocation: true` in the frontmatter of `SKILL.md` and with each other client's equivalent, such as `policy.allow_implicit_invocation: false` in `agents/openai.yaml` for Codex. Or it is loaded always, because the workspace's instructions tell the agent to load it at the start of every session; such a skill does not carry those flags, since in Claude Code the flag also blocks a load the instructions ask for, and in Codex it keeps the skill out of the list the model sees. A skill can also be loaded both ways: always in the workspaces whose instructions ask for it, and by the user everywhere else. It carries no flags either, for the same reason, and the user can still invoke it, because a skill without the flags remains a command. In every case the model never loads one of these skills on its own judgment, so a description is never what makes it load; for a skill without the flags, the description is what tells the model that the choice is not its own. Skip `skill-creator`'s advice on triggering — pushy descriptions, trigger phrases, description optimization — because it tunes a mechanism these skills switch off. Write the description as one plain sentence, because its readers are the user choosing a command and a maintainer, not a model deciding whether to load it: for a skill loaded always, when it is loaded, such as "Load at the start of every session in the team's support workspace."; for a skill the user invokes, what it is for; for a skill loaded both ways, what it is for and who loads it, such as "Curates the team's work folder; loaded by the user or by instruction." Leave out lists of what the skill can do, which `SKILL.md` already holds, and reasons meant to persuade the model. Which way a skill is loaded is the user's decision, so ask the user before you set it for a new skill or change it for an existing one, including one you find loaded neither way.

A skill can be the pair of a system prompt: the prompt holds the instructions, and the skill holds the references and scripts the prompt reads from. Such a skill is loaded always in the sessions that run under that prompt, because the prompt tells them to load it at the start, and never in a session under another prompt, even one opened in the same workspace. It carries no flags, for the reason above. Its description is what keeps other sessions away from it, so it names the prompt and nothing else, such as "Used only with the system prompt team-lead." Its `SKILL.md` opens by saying the same, for a session that loads it by mistake, and then lists what the folder holds. The routing, which reference is read when, stays in the system prompt, because written in two places it would drift: do not move or copy it into `SKILL.md`. Do not ask the user to choose a loading mode for such a skill: the arrangement is the user's decision already.

## Write for the agent that will use the instructions

Keep actionable guidance, the reason behind it, and the evidence needed to check it. Leave out authoring history: discarded options, rollout status, migration notes, and dated provenance such as "(my rule, 2026-10-14)" or "these rules come from real sessions". An agent cannot act on where a rule came from, and a stranger cannot check it; that history belongs in the materials of the work that changed the skill. A note on who approved a passage's wording, or on what the user has not yet confirmed, is history of the same kind and stays out too, unless the agent needs it as evidence or to know what is authorized. Settle what the user's words and the text settle: correct a defect, and make the editorial choice. When a substantive doubt remains whether a passage suits the user, do not resolve it with such a note, and do not delete supported meaning to make a note true: report the doubt, so that it reaches the user as a blocker, as `references/blockers-management.md` describes.

Organize detail by when the reader needs it. `SKILL.md` says when to read each reference rather than summarizing it, because a summary costs context on every load and drifts from the reference it repeats. For a skill paired with a system prompt, the prompt says when, and `SKILL.md` only lists what is there.

What the user says is evidence of a need, not text for the instructions. The user says what they need, in a remark to an agent, a correction, a label or a metaphor, and is not the author of the instructions: carrying the user's sentences into them, translated or not, is like pasting a requirement into a program's source. Read the source in full, headings included, with the situation each remark was made in; find what the user needs; and write the behavior that meets it, with the reason behind it, as you would write any instruction. In a later revision, what must survive is that need, not the wording that served it before. Keep the user's metaphor in the skill wherever it helps the model grasp why — a well-chosen metaphor can help convey intent where a rigid rule would not, as `skill-creator` itself advises — but never in place of the behavior, and do not spend the work evaluating or replacing the label with another one.

Some of the user's words point to no behavior at all. When the user says what the agent is rather than what it does — a portrait, a list of names of thinkers, schools or traditions — the meaning and its power to evoke are the content. Keep the names and the formulations the user chose deliberately, and where the user asks for a translation or for better writing, craft the wording: such a passage is written, not copied. Write no behavior beside it and no explanation of the names. A name in a prompt does more than inform the model: it is there to bring the tradition it names into play and to shift the way the model thinks, and an explanation beside it puts its own content in the name's place. Add no key that tells the model how to read them either. A personality written this way is meant to work by enchantment, not by analysis: it is an attempt to break through the client's default manner and carry a way of thinking into the model, and any analytic insert — a gloss, a procedure, a note on how to read — turns it back into a rule. That is why such a personality is best placed in the system prompt, the base every turn starts from, rather than in a skill loaded later, and why this understanding stays here, with those who write instructions, and never goes into the personality's own text.

Before you rewrite a passage, name the function it serves in the instructions and every need it carries, then check that each one survives the rewrite. Fixing a defect in a passage, such as a reference that cannot be resolved, does not license changing what the passage is for: remove the defect, not the purpose.

## Put each rule in the narrowest place it belongs

A rule for one part of a skill goes into that part's reference; a rule for the whole skill goes into its `SKILL.md`; a rule for a wider audience goes into the shared instructions that audience loads, such as a system prompt. A rule placed too wide starts governing work it was never meant for. Always edit the source of a skill, never a deployed copy.

## Write to open-source standard by default

All instructions are written as if they were going into a public open-source repository, whether or not it is published yet, so that they never need a separate cleanup before release:

- **Native American English, written rather than translated.** When the source material is in another language, write the passage anew as an American engineer would, instead of translating it: translated text keeps the other language's structure, calques and quotation marks. Use US spelling and straight quotes.
- **Nothing personal or private.** No personal names, private ticket codes, private skills, paths into private folders, or details of one machine. An example taken from the user's own work is adapted into a generic one that nothing ties to the user, not just stripped of its names; codes and paths use placeholders such as `ABC001` that cannot be mistaken for real items.
- **Examples name no real skill.** Real skills change, and an example that describes one goes stale with it and then teaches the reader the old arrangement; describe the kind of skill instead.
- **Other languages only when they are the point**, for example test strings that check Unicode handling.
- **Readable as raw Markdown.** Reference files by backticked paths relative to the root of the skill or repository, never by `[text](link)`: in raw Markdown the caption hides the address.
- **One name per concept**, in prose and in the output of helper scripts alike, so a reader never wonders whether two words mean two things.
- **One line per paragraph and per list item.** Hard wraps split one thought across lines and make diffs noisy.

## Scripts and tests are part of the skill

Helper scripts bundled with a skill are the skill author's work, not a separate product-development assignment. When applying an explicitly agreed change, keep instructions, helper scripts and tests consistent, and do not defer the Python part merely because it is code. Carrying out an agreed change does not grant permission for other work the change did not include.

Mechanical determinations belong to scripts, not to agents. When a procedure is a mechanical rule — picking the last matching entry in a list, comparing identifiers, choosing a delivery address, applying per-client lookup heuristics — put it in a helper script and keep it out of the instructions an agent must follow. A helper script applies such a rule cheaply and exactly; for an agent it costs attention and invites mistakes. Instructions tell the agent what to do and what to report, and the helper script decides the rest.

Tests read and write files with an explicit UTF-8 encoding, so they pass under a C or POSIX locale as well.

## Check before handing it over

Have the whole of the instructions reviewed — the entire skill or the entire prompt — by a separate agent with a fresh context, not just the diff: defects in long-committed text are as real as new ones. The reviewer reads every file in full, does not edit, and reports numbered findings with file, line, severity, the current text and a replacement. A useful rubric:

- public-repository fitness: names, private codes, paths and skills, machine details;
- language: text in another language without a reason, translated-sounding English, non-US spelling or typography;
- coherence: contradictions, the same rule stated in two places, references to files, sections, tools or fields that do not exist, terms used without definition;
- instructional quality: reasons given, no unexplained rigid rules, references read at the right time, no authoring history;
- formatting: hard line breaks, broken Markdown;
- skill loading: the invocation flags match how the skill is loaded in every client it ships for, and the description is one plain sentence as "The model never chooses a skill" describes;
- scripts and tests: they pass, and the references describe what each helper script actually does.

For a skill, confirm that it loads the way it is meant to: for a skill the user invokes, ask the user to invoke it, such as by its slash command in Claude Code, since an agent cannot load such a skill itself; for a skill loaded always, confirm that a fresh session in the workspace loads it at the start; for a skill loaded both ways, confirm both; for a skill paired with a system prompt, confirm that a fresh session under the prompt loads it at the start and that a session under another prompt in the same workspace does not, that every path the prompt and the references name resolves in the deployed copy, and that the helper scripts run from there. Fix the findings, then run a second pass that checks each fix and looks for defects the fixes introduced; replacements made by a script or a regex are a common source of new ones. Test the instructions wherever testing fits the change and is simple to set up — run the helper scripts' tests, or a few test prompts against the old and new text as `skill-creator` describes for testing a skill's behavior, not its triggering. When meaningful testing would be complex or costly, do not skip it silently and do not build it on your own: ask the user, proposing a concrete test — what to run, on which prompts or cases, and what it would show. Commit according to the repository's own rules.
